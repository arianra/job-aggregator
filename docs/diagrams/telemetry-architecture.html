Why rrweb, not a platform

  • • Sentry, PostHog & Highlight all build replay ON rrweb — using it directly gets the same fidelity
  • • Platform self-host floors: OpenReplay 8 GB · Highlight 8 GB + Kafka/ClickHouse · PostHog 16 GB & officially unsupported · Sentry 16 GB + 40 containers
  • • rrweb is MIT, ~23 KB gz record-side, plain JSON events — greppable without vendor APIs
  • • web-vitals (3 KB, Apache-2.0) adds CLS/INP/LCP/FCP/TTFB

One envelope, one timeline

  • • Fixed envelope: ts · seq · sessionId · requestId · actor · source · type · name · payload
  • • type is a CLOSED enum (validated by zod); name is an OPEN dot-vocabulary (ui.click, error.http)
  • • Store: one JSONL file per UTC day + index.json manifest — grep/jq IS the query language
  • • requestId doubles as trace-id; real W3C traceparent is one middleware line away if OTel ever lands

Phases & escape hatches

  • • P0 correlation foundation (ALS + X-Request-Id + request-completed line) — useful alone
  • • P1 semantic timeline (SDK + ingest + events CLI) · P2 DOM replay (rrweb + /debug/replay) · P3 analytics niceties
  • • winston kept; pino optional (O1) · Spotlight-by-Sentry = documented add-on if error grouping hurts (O3)
  • • If human dashboards ever matter: migrate to OpenReplay — never build dashboards here
